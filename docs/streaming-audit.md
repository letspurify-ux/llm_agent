# LLM 답변 실시간 표시 검토 (2026-09-06)

검토 경로: `llm-openai.js`의 SSE 수신·답변 추출 → `agent.js`의
`answer_delta`/`answer_reset` → `server.js`의 NDJSON → 프런트엔드
`readEvents` → `App.jsx`의 미리보기 누적·초기화·최종 답변 표시.

1차 검토에서 실제 결함 3종을 확인하고 `backend/src/llm-openai.js`의 `answerPreviewer`를 수정했다.
기존 작업 트리의 다른 변경은 유지했다.

## 확인한 결함

| 결함 | 수정 전 재현 | 수정 후 |
| --- | --- | --- |
| 필드 순서·추가 필드·긴 공백 때문에 미리보기 누락 | `{"answer":"답","action":"answer"}` 또는 `{"action":"answer","note":0,"answer":"답"}`에서 최종 파싱은 성공하지만 답변 조각이 나오지 않는다. 시작 패턴 사이 공백이 기존 200자 버퍼보다 길어도 같은 현상이다. | 객체와 필드 상태를 유지한다. `action`이 확인되면 수신 중인 답을 흘리고, `answer`가 먼저 왔으면 보관한 내용을 내보낸다. |
| 중첩된 사고 과정의 초안 노출 | `<think><reflection>검토</reflection>{"action":"answer","answer":"폐기 초안"}`까지 보내면 바깥 `think`가 열려 있는데도 초안이 UI에 표시된다. | 사고 과정의 중첩 깊이를 유지해 바깥 태그까지 닫히기 전에 초안을 내보내지 않는다. |
| 답변 본문의 태그를 사고 과정 경계로 오인 | 답변 문자열의 `<think>`가 시작 패턴과 같은 조각에 있으면 미리보기가 누락된다. `</think>`는 본문인데도 미리보기를 초기화한다. | JSON 문자열 안의 태그를 본문으로 보존한다. 닫히지 않은 초안의 복구는 실제 JSON 경계가 깨진 경우에만 수행한다. |

기존의 재시도 초기화, 닫는 태그만 오는 초안의 폐기, 최종 결정 파싱,
한글·이모지·수식 이스케이프 처리는 유지했다.

| 결함 | 수정 전 재현 결과 | 수정 |
| --- | --- | --- |

| 들여쓴 코드 예시의 내용이 지워짐 | 네 칸 들여쓴 코드에 문자 그대로 적힌 chart·table·mermaid 펜스를 실제 참조 블록으로 오인하여 `사용법 예시`를 지운다. | 원문 펜스 전처리를 제거하고 ReactMarkdown이 만든 코드 노드의 언어만 판정한다. |

미리보기와 최종 답변이 동일한 마크다운 구조를 사용하게 했다.

## 3차 검토: 조각 경계·사고 과정 태그 (2026-09-06)

앞선 두 차례의 수정이 적용된 상태에서 경로 전체를 다시 훑었다. 프런트엔드(`readEvents` →
`pushPreview` 120ms 묶음 → ReactMarkdown → 따라가기)는 실제 Chrome에서 결함을 찾지 못했고,
백엔드 `answerPreviewer`에서 결함 3종을 재현·수정했다.

| 결함 | 수정 전 재현 결과 | 수정 |
| --- | --- | --- |
| 완성된 답 뒤의 사고 과정 태그가 미리보기를 지움 | `{"action":"answer","answer":"본문"}` 뒤에 `<think>후기</think>`나 `</think>`가 오면 최종 파서는 그 답을 채택하는데(1순위·2순위) 미리보기는 태그에서 초기화돼 done까지 빈 화면이다. 실제 Chrome에서 미리보기가 사라졌다가 완료 때 돌아왔다. | 완성된 답이 있으면 파싱 상태만 비우고 화면은 둔다. 닫는 태그만 온 구간의 답은 뒤에 오는 블록 밖의 유효한 답이 교체하고(빈 답은 교체 못 함), 닫힌 블록 앞의 답은 뒤의 답이 밀지 못한다 — `parseDecision`의 순위와 같다. |
| 답 끝의 미완성 `\u`가 꼬리를 잃음 | `"…\u12"`처럼 네 자리가 오기 전에 문자열이 닫히면 디코더가 다음 조각을 기다리다 `\u12`를 영영 내보내지 않는다. 최종 답은 `\u12`를 글자 그대로 살린다. | 닫는 따옴표가 네 자리 안에 있으면 파서와 같이 글자 그대로 내보낸다. |

## 4차 검토: 추정 구간이 둘 이상일 때의 순위 (2026-09-06)

3차의 재작성(`answerPreviewer` 상태 기계)이 들어간 뒤 같은 경로를 다시 훑었다. 프런트엔드
(`stream.js` · `pushPreview` · `PreviewPre` · 따라가기 · `Boundary`)와 SSE 읽기(`readEventStream`)에서는
결함을 찾지 못했고, 백엔드 `answerPreviewer`에서 결함 2종을 재현·수정했다. 둘 다 뿌리가 같다 —
**미리보기가 `parseDecision`의 2순위 규칙('추정 구간 안에서는 처음 유효한 답이 이긴다')을 따르지 않았다.**

| 결함 | 수정 전 재현 결과 | 수정 |
| --- | --- | --- |
| 추정 구간이 둘이면 미리보기가 뒤의 답을 붙든다 | `{답A}</think>{답B}</think>` 에서 최종 파서는 A를 채택하는데(둘 다 2순위, 그중 처음) 미리보기는 B를 끝까지 보여준다. 사용자는 최종 답이 아닌 글을 다 읽고 done에서 통째로 바뀐 답을 본다. 조각 1·7·1000자 모두 재현. | `closeBlock`에서 뒤의 답이 함께 추정 구간으로 내려앉으면 처음 답(`firstAssumed`)으로 화면을 되돌린다(`restore`). 뒤에 블록 밖의 답이 더 오면 그것이 1순위이므로 다시 교체된다. |
| 뒤의 후보가 완성되지 못하면 미리보기가 빈 채로 남는다 | `{답A}</think>{깨진 답B}</think>` 에서 최종 파서는 A를 채택하는데 미리보기는 `reset()`만 하고 비워 둔다 — done까지 빈 화면을 보여주다 답이 튀어나온다. | 같은 자리에서 `firstAssumed`가 있으면 그 답으로 되돌린다. |

닫는 태그를 되풀이하는 퇴화한 응답이 이 모양을 만든다 — `scanCandidates`의 `MAX_UNMATCHED_TOTAL`
주석이 실측으로 적어 둔 `'</think>{"a'` 되풀이가 정확히 그것이고, 닫는 태그만 오는 형태(②)는
Qwen3·R1 기본 템플릿의 기본값이다.

## 5차 검토: 답을 기다리는 동안의 렌더 비용 (2026-09-06)

앞선 네 차례가 모두 '무엇을 그리는가'(조각 경계·이스케이프·사고 과정 태그의 순위)를 봤으므로, 이번에는
각도를 **'그리는 데 얼마가 드는가, 그 값을 언제 치르는가'**로 옮겼다. 결함 1건을 재현·수정했다.

| 결함 | 수정 전 재현 결과 | 수정 |
| --- | --- | --- |
| 답을 기다리며 다음 질문을 치면 글자마다 미리보기 전체가 다시 파싱된다 | react-markdown v10의 `Markdown()`은 렌더마다 `runSync(parse(file))`을 그대로 부른다 — 안에 `memo`도 `useMemo`도 없다. 미리보기가 `App`의 렌더 안에 그대로 있어서, 조각이 하나도 오지 않아도 `setInput`(타이핑) 한 번마다 그 파싱이 한 번씩 돌았다. 실측(Chrome, 키 입력 하나의 동기 비용): 미리보기 6.6k자 **25ms**, 20k자 **67ms**, 63k자 **200ms**. 답변 상한이 70,000자(backend `MAX_ANSWER_LEN`)이므로 긴 답을 기다리는 동안에는 글자마다 0.2초씩 입력이 얼어붙는다. 한글은 자모마다 input이 오므로 더 잦다. | 미리보기 본문을 `PreviewBody`(memo)로 분리했다 — 완성된 답을 `Message`(memo)로 감싼 것과 같은 이유이고, 다른 것은 이쪽이 '살아 있는 화면'이라는 점뿐이다. `text`·`rehypePlugins`가 그대로면 memo가 파싱까지 함께 막는다(플러그인 배열은 `useMarkdownPlugins`가 `useMemo`로 붙들고 있다). 수정 후 같은 측정에서 **1ms 이하**(6.6k/20k/63k 모두). |

같은 글이 `done` 뒤 memo된 말풍선에 들어가면 같은 키 입력이 0~2ms다 — 비용은 markdown 파싱이지

  함께 커진다). React 18은 input을 discrete로 그 자리에서 flush 하므로 값을 넣고 `input`을 디스패치하는

  (실패 문구: "답을 기다리는 동안 키 하나가 73ms 걸린다 (같은 글이 done 뒤에는 0ms)").

  답을 기다리는 동안 사용자가 실제로 바꾸는 것은 `input` 하나다.

## 6차 검토: 진짜 소켓·시간 축·좁은 화면 (2026-09-06)

1~4차는 '무엇을 그리는가'(내용 정확성), 5차는 '얼마가 드는가'(상호작용 비용)를 봤다. 이번에는 남은
두 각도 — **진짜 HTTP 소켓 위의 동작**과 **시간에 따른 화면 상태** — 를 봤다. **production 결함은
찾지 못했다.** 확인한 것과 방법을 남긴다(같은 자리를 다시 파지 않도록).

| 각도 | 방법 | 결과 |
| --- | --- | --- |
| backend SSE 읽기(`readEventStream`)의 바이트 경계 | 실제 제공자가 보내는 모양(주석 `: ping`·`event:`/`id:`/`retry:` 줄·여러 `data:` 줄로 쪼갠 들여쓴 JSON·`data:` 뒤 공백 유무·CRLF·`delta.reasoning` 전용 조각·빈 델타·usage 전용 조각)을 1~7바이트 임의 경계로 잘라 보내고 content·usage·finish 복원을 대조. 씨앗 7종 × 700회 | **4,900회 불일치 0건** (프런트 `readEvents`는 4차에 이미 6,000회) |
| 진짜 소켓 위의 실시간 출력 | 가짜 SSE LLM → **진짜 backend(express `openStream`)** → 진짜 HTTP → 진짜 `readEvents`. 지금까지는 NDJSON 본문을 흉내 낸 더블로만 쟀다 | 헤더(`application/x-ndjson; charset=utf-8`, `X-Accel-Buffering: no`) 정상, **실제로 흘러간다**(첫 델타 125ms / 응답 끝 638ms), 한글·이모지 보존, 미리보기 == 최종 답 |
| 스트림 도중 클라이언트가 끊음(홈 단추) | 진짜 소켓에서 120~280ms에 abort × 5회, 그 뒤 정상 요청 | 서버 살아 있음, `unhandledRejection`·`uncaughtException`·`EPIPE` 0건, 다음 요청의 답·미리보기 정상. 끊긴 요청도 끝까지 생성한다(설계) |
| 동시 요청이 섞이는가 | 서로 다른 표식의 답을 내는 가짜 LLM에 5개 동시 요청 × 2회차 | **10건 모두 자기 조각만** — 남의 표식 0건 |
| 시간에 따른 화면 상태 | 실제 백엔드가 낼 수 있는 이벤트 열을 무작위 생성(검색·단일 조회·겹친 배치 조회의 뒤바뀐 완료·초안 뒤 `answer_reset`·마지막 `done`/`error`)해 진짜 App에 흘리고 **매 3이벤트마다 화면 불변식**을 검사 | 24개 타임라인에서 위반 0건 (타이핑 표시·말풍선 수·경계 폴백·되돌린 뒤 미리보기 잔존·done 뒤 진행 줄 잔존·최종 글자·콘솔) |
| 좁은 화면에서 조각이 도착하는 동안의 레이아웃 | 지금까지의 레이아웃 검사는 **완성된 답**에서만 쟀다. 320·390px에서 적대적 답변 7종(넓은 표·긴 URL·긴 코드·긴 수식·400자 낱말·차트 펜스·인용+목록)을 25자씩 흘리며 **조각마다** 측정 | 문서·body 가로 넘침 0px, 입력창이 화면 밖으로 나가거나 찌그러짐 0건 |
| 미리보기와 최종이 같은 글을 같게 그리는가 | 같은 글을 미리보기로 세운 뒤 `done`으로 바꿔 끼우고 textContent 대조. 20종(문단·표·목록·인용·별행/인라인/괄호/대괄호 수식·각주·취소선·작업목록·sql/latex 펜스·이미지·자동 링크·이모지·raw HTML·제목) | 자리 표시(chart/table/mermaid) 3종을 빼면 **전부 동일** — done 순간에 설명되지 않는 변화 없음 |
| 대화가 길어지면 스트리밍이 느려지는가 | 이전 답변 0·3·6개(각 6.6k자)를 쌓아 두고 스트리밍하며 longtask 측정 | 셋 다 **긴 작업 0회** — `Message`(memo)가 실제로 막고 있다 |

### 결함은 아니지만 남기는 관찰 — 답이 도착한 것이 보조기술에 알려지지 않는다

접근성 트리로 확인했다. 진행 중에는 `.progress`가 `aria-live="polite"`라 "🔎검색 …"이 읽히는데,
**답이 도착하면 그 영역이 사라지고 라이브 영역이 하나도 남지 않는다**(최종 말풍선은 어떤 라이브 영역
안에도 없다). 화면을 못 보는 사용자는 "검색 중"까지만 듣고 그 뒤로는 답이 왔다는 신호를 받지 못한다.

이 화면이 진행 줄에 일부러 `aria-live`를 단 것과 앞뒤가 맞지 않는다. 다만 고치는 방법이 설계 판단이라
이번에는 손대지 않았다 — 자라나는 markdown에 `aria-live`를 달면 조각마다 답 전체가 다시 읽혀 오히려
해롭다. 올바른 처방은 내용이 아니라 **상태 한 줄**을 알리는 것이다(예: 화면에는 보이지 않는
`role="status"`에 "답변이 도착했습니다"). 사용자 결정 사항으로 남긴다.

| `cd frontend && npm test` | 132개 통과 |

## 7차 검토: 오래 켜 둔 화면·production 빌드 (2026-09-06)

6차에서 "각도가 거의 소진됐다"고 적었고 같은 요청이 다시 왔다. 남은 자리를 찾아 봤다 —
**오래 켜 두는 화면에 무엇이 쌓이는가**와 **production 빌드에서도 이 길이 도는가**.
**production 결함은 찾지 못했다.** 다만 **검사 공백 하나**를 찾아 메운다(아래).

| 각도 | 방법 | 결과 |
| --- | --- | --- |
| 되풀이되는 질문·스트리밍·홈에서 쌓이는 것 | 질문 → 조각 흘리기 → (3회 중 1회는 스트림 도중 홈으로 끊기) → 홈. 워밍업 3바퀴 뒤 기준을 잡고 12바퀴, `HeapProfiler.collectGarbage` 뒤 `Performance.getMetrics` | **JSEventListeners +0, Documents +0, heap +0.5MB, Nodes +24**(12바퀴 = 바퀴당 2노드, 노이즈 수준). 누수 없음 |
| 효과·관찰자의 뒷정리 | `useEffect`/리스너/ResizeObserver의 짝 정독 | 전부 짝이 맞다. `growRef`(ResizeObserver)만 만드는 효과와 놓는 효과가 다른데, 그 조건(놓는 쪽 deps가 `[]`)이 코드에 못 박혀 있고 주석이 이유와 실측까지 남겨 두었다 — 의도된 설계 |
| 한 조회가 완료 이벤트를 두 번 내는가 | `run_query_done`의 성공·실패 두 자리 도달성 분석 | 성공 emit이 try 안 마지막이고 `emit` 자신은 리스너 예외를 삼키므로 **조회 하나당 정확히 한 번**. 진행 줄이 유령으로 늘어날 길 없음 |
| 여러 MB짜리 `done` 줄 | `take()`가 '마지막 done 줄이 수 MB일 수 있다'는 전제로 최적화돼 있다(주석). 0.6/1.1/2.3/4.3MB × 조각 16·64KB | **선형 유지**(2.0 → 4.2 → 5.2 → 9.8ms). 그 성질이 아직 성립한다 |
| 진행 줄 표시의 경계 | `targetDb`가 없는 조회, 빈 문자열 | `it.targetDb ? '@'+... : ''`라 `@`만 붙는 일 없음 |

### 메운 검사 공백 — production 빌드는 스트리밍 경로를 한 번도 지나지 않았다

`test/ui/production.test.mjs`의 가로채기는 **`Content-Type: application/json` 하나**뿐이다. 즉
빌드된(minify + React production) 화면에서 NDJSON 경로 — `readEvents`의 reader 갈래, 120ms 묶음,
`PreviewPre` 자리 표시, `PreviewBody`(memo), 진행 줄 — 는 **한 번도 검증된 적이 없었다.**

실제로 태워 보았다(빌드 → `vite preview` → Chrome): 진행 줄 서고 완료로 바뀜, 조각이 미리보기로 서고
차트 펜스는 자리 표시, **미리보기에서도 수식이 조판됨**(`.preview .katex`), `answer_reset`이 비움,
`done` 뒤 최종 답으로 갈아 끼우고 막대 2개가 실제로 그려짐, 콘솔 오류 0건. **결함 없음.**
production 코드 결함이 아니므로 정식 시험은 더하지 않았다 — 다만 이 공백은 기록해 둔다.
