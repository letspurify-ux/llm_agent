# 긴 인라인 수식 배치 검토 — 2026-09-09

## 재현과 원인

320px 화면의 `인용 → 목록 → 인라인 분수`에서 수식의 실제 폭은 505.28px,
컨테이너 폭은 168px이었다. 링크 안에서는 같은 수식에 268px만 주어졌다.
기존 인라인 요소에는 스크롤 상자가 없어 말풍선의 `overflow-x: clip`이
뒷부분을 잘랐다. 페이지 가로 넘침이 없다는 검사만으로는 이 손실을 알 수 없다.

모든 수식에 `inline-grid`와 스크롤을 주면 짧은 `$x^2$`의 높이도 20px에서
약 41px로 바뀌었다. 따라서 전역 CSS 교체는 문장 배치를 보존하지 못한다.

## 변경

[InlineMath](../frontend/src/InlineMath.jsx)는 실제 줄을 배치하는 가장 가까운
컨테이너의 내용 폭과 KaTeX의 줄바꿈 불가능한 `base` 단위 폭을 비교한다.
컨테이너보다 넓은 단위가 있을 때만 스크롤 상자로 전환한다. 짧은 수식과
여러 단위 사이에서 자연스럽게 줄바꿈할 수 있는 수식은 원래 배치를 유지한다.

- 문단·제목·강조·링크·중첩 목록·인용·각주가 같은 배치 규칙을 사용한다.
- 표 안 수식은 표의 기존 가로 스크롤을 사용하고, 별행 수식은 기존 렌더러가 처리한다.
- 글꼴 로딩과 컨테이너 크기 변경 때 다시 측정한다. 넓어진 화면에서는 불필요한 스크롤을 해제한다.
- 일반 수식 스크롤은 키보드로 접근할 수 있다. 링크 안에는 추가 포커스 대상을 만들지 않는다.
- 인쇄에서는 스크롤 상자의 전체 수식 폭에 축척을 적용한다. 여러 `base`가 이어진 수식도 포함한다.
- 미리보기와 최종 답변은 같은 React 컴포넌트를 사용한다. 교체·초기화 때 관찰 대상과 이벤트를 정리한다.

## 검증

[실제 앱 회귀 검사](../frontend/test/ui/inline-math.test.mjs)는 API 스트림을
고정 입력으로 대체하고 실제 App을 실행한다. 개발 서버와 현재 소스로 새로
만든 production 빌드에서 각각 다음을 확인한다.

- 정확한 TeX 원문, 이웃 chart·Mermaid·각주와 표의 보존.
- 320→1,000→320px 전환, 수식 시작과 끝에 실제 스크롤로 도달.
- 짧은 수식의 20px 높이와 기존 문장 줄 높이, 분수·근호의 세로 배치.
- 링크 주소·새 탭 동작의 속성과 중첩 포커스 요소 부재, 일반 수식의 화살표 키 스크롤.
- 부분 스트림·최종 답변, 인쇄 CSS의 수식 폭과 실제 PDF 생성, 화면 복귀.
- 초기화 뒤 관찰 대상 수 복원, 페이지 넘침·콘솔 오류 없음.

두 검사가 모두 통과했다. `npm --prefix frontend run test:inline-math`로 실행하며,
필수 `test:regression`에도 포함되어 Chrome이 없으면 실패한다. 320px 캡처에서도
짧은 수식, 중첩 분수, 제목·링크, 높은 분수와 이어진 수식의 배치를 확인했다.
전체 구조 변경의 통합 검증 결과는 [완료 검토 기록](nested-rendering-follow-up.md)에 기록한다.
