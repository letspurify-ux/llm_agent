# 관리자 화면 검토 (2026-09-09)

검토 범위: 기존 페이지에 추가한 DB·지식·방법·쿼리 관리, 서버 검색, 편집·삭제,
인증과 비밀번호 처리, 관리자 화면 전환이 채팅에 미치는 영향.
기존 자료를 변경하는 실험은 하지 않고, 임시 MariaDB와 브라우저 대역 데이터로 결함을 재현했다.

## 재현한 결함과 수정

| 우선순위 | 재현 조건과 영향 | 수정 |
| --- | --- | --- |
| P1 | 두 화면에서 같은 항목을 연 뒤 순서대로 저장하면, 나중 저장이 먼저 저장한 내용을 조용히 덮어쓴다. 오래된 화면에서 삭제도 가능했다. | 읽은 항목의 revision을 PUT/DELETE의 `If-Match`로 확인한다. 트랜잭션 안에서 행을 잠근 뒤 검사하여 충돌하면 409, 버전 누락이면 428로 거부한다. 입력 초안은 유지한다. |
| P1 | SQL로 등록한 대상 DB 목록에서 이름 둘레에 탭·개행·유니코드 공백이 있으면, 실행 시에는 DB를 찾지만 삭제 검사는 사용 중인 DB로 인식하지 못했다. | SQL 참조 검사의 공백 제거를 실행 경계의 `String.trim()`과 맞췄다. 탭·개행·NBSP·전각 공백·BOM 등을 재현 검사한다. |
| P2 | 대상 DB 선택 목록의 검색창에서 Enter를 누르면 검색 중이던 쿼리의 다른 변경 사항까지 저장했다. | 해당 검색창의 Enter가 바깥 편집 폼을 제출하지 않도록 처리한다. 실제 브라우저 키 입력으로 확인한다. |
| P2 | 기존 쿼리에 더 이상 등록되지 않은 DB 이름이 남아 있으면, 선택 목록에 나타나지 않아 해제할 수 없었다. 새 DB를 선택해도 유효하지 않은 이름이 함께 저장 요청에 남았다. | 현재 선택한 이름을 별도로 표시하고 각각 해제할 수 있게 했다. 이전 DB를 제거하고 새 DB로 복구하는 과정을 검사한다. |
| P2 | 여러 줄 질문을 작성하고 관리자 화면에서 창 크기를 바꾸면, 채팅으로 돌아온 뒤 질문 일부가 가려지고 스크롤도 꺼져 있었다. | 숨겨진 입력창의 높이를 측정하지 않고, 채팅 복귀 시 표시되는 폭에 맞춰 높이를 다시 계산한다. |
| P2 | 긴 대화의 중간을 읽다가 관리자 화면을 왕복하면 읽던 위치에서 벗어났다. 숨겨진 채팅의 0 크기를 바닥 도착으로 해석하고 스크롤을 변경했다. | 숨겨진 채팅의 크기·스크롤 이벤트는 위치와 따라가기 상태를 변경하지 않도록 하고, 관리자 화면을 열 때 진행 중인 자동 스크롤을 멈춘다. |

## 회귀 검사

- [백엔드 단위 검사](../backend/test/admin.test.js): 입력 검증, SQL 바인딩, 비밀번호 유지,
  인증, 안전한 오류 응답, revision 없이 수정·삭제 시 DB 접근 전 거부.
- [실제 MariaDB 검사](../backend/test/integration/mariadb.test.js)의 `관리자` 테스트:
  CRUD·검색·페이지 이동, 특수 공백 참조, 두 동시 저장 중 한 건만 허용,
  실제 HTTP GET/POST/PUT/DELETE의 ETag/If-Match, 비밀번호만 변경했을 때도 오래된 수정·삭제 거부.
- [관리자 브라우저 검사](../frontend/test/ui/admin.test.mjs): 검색·페이지 이동·오류 복구·인증,
  검색 Enter, 오래된 편집 초안 보존, 잘못된 DB 선택 복구, 삭제 확인,
  작은 화면, 여러 줄 질문과 읽던 대화 위치 보존. 개발 서버와 실제 빌드 결과에서 모두 실행한다.
- 기존 채팅의 전체 필수 회귀는 `frontend`의 `npm run test:regression`으로 실행한다.

최종 결과: 백엔드 단위 검사 583개, 실제 MariaDB·HTTP 관리자 검사 4개,
전체 필수 회귀(프론트엔드 단위 검사 347개, 채팅 브라우저 89개, 관리자 개발/빌드 2개,
기존 빌드 검사 4개, 인라인 수식 2개, 백엔드 렌더링 경계 150개) 모두 실패 없이 통과했다.
기존 페이지의 관리자 목록·상세 API가 200으로 응답하고 revision/ETag가 일치하는 것도
읽기 요청으로 확인했다.

## 설정 및 검증 한계

검토 시 현재 환경의 `ADMIN_TOKEN`은 미설정이었다. 이 설정에서는 서버에 접속 가능한 사람이
관리 데이터를 조회·변경할 수 있다. `X-Admin-Request`는 교차 출처 폼 제출을 막는 장치이며
관리자 인증을 대신하지 않는다. 인증이 필요한 환경은 `backend/.env`에 `ADMIN_TOKEN`을 설정하고
백엔드를 재시작해야 한다. 이번 검토에서는 인증 키와 운영 데이터를 변경하지 않았다.

revision은 비밀번호가 포함된 원본의 지문을 서버의 비공개 키로 HMAC 처리한 값이다.
원본 비밀번호와 지문은 응답에 포함하지 않는다. 서버를 재시작하면 키도 바뀌므로 열린 편집기는
항목을 다시 읽어야 한다. 별도의 스키마 변경은 필요 없다. 이 키는 프로세스별로 다르므로
현재의 단일 프로세스 실행 구성을 전제로 한다. 여러 인스턴스에 요청을 분산하려면
비공개 서명 키를 공유하는 구성이 추가로 필요하다.

Oracle 실제 접속·SQL 실행의 성공 여부, 대규모 운영 데이터에서 검색 성능은 이번 관리자
회귀 검사의 범위 밖이다. 관리자 SQL 검증은 기존 SELECT/WITH 허용 규칙을 재사용하며,
SQL 문법·스키마·권한에 따른 실행 성공을 보장하지 않는다.
