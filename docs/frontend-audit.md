## 검증 결과

- 단위·실행 스크립트 테스트: **121개 통과**, 실패·건너뜀 0개.

- `git diff --check`, 수정한 Bash 스크립트 구문 검사 통과.

기존 검증에는 수식·차트 파싱과 렌더, 오류 폴백, 링크·이미지 정책, 검색·조회 진행,
IME 전송, 좁은 화면·인쇄, 스크롤과 테스트 프로세스 정리가 포함된다.

홈 복귀 뒤 옛 스트림이 새 대화의 상태를 변경하지 않는 동작을 확인했다.

production 테스트는 현재 소스를 새로 빌드하고 Vite preview의 실제 `dist/index.html`을 연다.
답변·수식·차트·흐름도·조회 표, 후속 질문의 이력, 홈 복귀와 콘솔 오류를 확인한다.
화면 캡처도 육안 확인했으며 테스트가 생성한 서버와 Chrome은 종료했다.

재실행:

```bash
cd frontend
npm run test:all
```

이 명령은 `npm test`, `npm run test:ui`, `npm run test:production`을 순서대로 실행한다.
`test:production`만 별도로 실행해도 현재 소스를 다시 빌드한다.

## 추가 정밀 검토 — 2026-09-06 (입력 기전 중심)

앞선 회차들이 답변 내용·레이아웃·스트림 경로를 훑었으므로, 이번에는 각도를 **실제 입력 기전**
(진짜 IME 조합·진짜 손가락·진짜 마우스)과 **아직 재보지 않은 출구**(인쇄, CSV 파일, 복사되는 글)로 옮겼다.
검토 시작 시의 전체 테스트는 단위 129개, Chrome UI 54개, production 2개로 모두 통과했다.

### 재현하고 수정한 결함 1건

| 결함 | 수정 전 재현 | 수정 | 정식 회귀 테스트 |
|---|---|---|---|
| 밀어 둔 Enter가 있으면 Alt·Shift+Enter가 줄바꿈 대신 **질문을 전송** | 조합 중에 Enter를 누르면 확정될 때까지 밀어 두는데(`pendingSendRef`), 이어서 Alt·Shift+Enter로 줄을 바꾸면 `endComposition`의 `blur`가 조합을 확정시키고 그 `compositionend`가 `blur`보다 **먼저** 온다 — `onCompositionEnd`가 그것을 'IME가 확정했다'로 읽고 쓰다 만 질문을 보냈다. 실측: 질문 말풍선이 서고 입력창에는 방금 넣은 줄바꿈 하나(`'\n'`)만 남았다 | 조합을 우리가 직접 끝내는 자리(`endComposition`)에서 `blur` 앞에 밀어 둔 Enter를 지운다. 그 함수를 부르는 자리는 줄바꿈뿐이므로, 줄을 바꾸겠다는 것은 그 Enter를 무르겠다는 뜻이다. `onBlur`의 같은 지우기로는 막지 못한다 — 그쪽은 `compositionend` 뒤다 | `test/ui/ui.test.mjs`: 밀어 둔 Enter가 있어도 Alt·Shift+Enter는 줄만 바꾼다 |

재현에는 CDP의 `Input.imeSetComposition`으로 렌더러에 **진짜 조합**을 걸고 초점 에뮬레이션을 켰다.
흉내 낸 `CompositionEvent`로는 이 결함이 보이지 않는다 — `blur`가 조합을 확정시키는 그 순간 자체가
생기지 않기 때문이다(기존 IME 회귀 테스트가 그 방식이라 이 자리를 지나쳤다).
새 테스트는 수정을 되돌려 실제로 실패하는 것을 확인했고(`Alt+Enter로 줄을 바꿨는데 쓰다 만 질문이 나갔다`),
그때 기존 IME 테스트는 그대로 통과해 두 시험이 다른 것을 지키고 있음도 확인했다.
`test/ui/driver.mjs`의 `page.key`에 수식키(modifiers) 인자를 더했다.

**노출 범위**: 물리 키보드에서는 수식키 자체의 `keydown`(`key: 'Alt'`)이 먼저 와 밀어 둔 Enter를 지우므로
대개 이 길로 가지 않는다(실측으로 확인). 조합키를 수식키 `keydown` 없이 보내는 경로(일부 소프트 키보드·
키 리매핑·자동화)에서 드러난다. 고치는 값이 한 줄이고 다른 동작에 영향이 없어 그대로 막았다.

`Element.prototype.scrollTop`의 setter를 감싸 스택으로 재었다. 답은 앱 자신이었다(`App.jsx`의 glide step).

### 재현하고 수정한 결함 1건

| 결함 | 수정 전 재현 | 수정 | 정식 회귀 테스트 |
|---|---|---|---|
| **따라가기가 도는 동안 무언가를 펼치면 보던 자리를 잃고 바닥으로 끌려간다** | glide의 step은 매 프레임 `target()`을 다시 잰다(그래야 내려가는 동안 늦게 서는 차트까지 따라간다). 그 사이에 ⚡ 패널을 펼치면 펼쳐서 자란 높이가 그대로 새 목표가 되어 끝까지 끌려간다. 떼어 둔 표시(`stuckRef`)는 '앞으로 시작할' 미끄러짐만 막고 이미 도는 것에는 닿지 않는다. 실측 ① 답이 온 뒤 600ms 안에 펼치면 패널 머리가 화면 위로 513px 밀려났다(600ms 뒤에 펼치면 멀쩡 — 그래서 빠른 기계에서는 지나갔다). ② 질문을 보낸 직후(내 말은 언제나 바닥으로 미끄러진다) 앞 답변의 ⚡을 펼치면 **펼치는 순간을 기준으로 1,197~2,408px** 끌려가고 패널 머리가 화면 위 1,813px로 사라졌다 | `unstick()`이 `stopGlide()`를 함께 부른다 — 끌기 시작·안쪽 스크롤·대화 밖 휠이 사용자의 개입에서 모두 그렇게 하는 것과 같은 처방이다 | `test/ui/ui.test.mjs` 1개 추가(따라가기가 도는 동안 펼쳐도 보던 자리는 그대로다). 앞 회차가 늘린 전제는 되돌렸다 — 그 시험은 처음부터 이 결함을 잡고 있었다 |

수정 뒤 사람이 누를 수 있는 간격 다섯(16·60·150·300·340ms) 모두에서 펼침이 보던 자리를 **0px** 움직인다.
새 시험은 '펼치는 그 순간'을 기준으로 잰다 — 그 전의 움직임은 내가 보낸 말을 따라간 정당한 것이라 빼야 하고,
그것까지 세면 고쳐도 실패한다(처음에 그렇게 재어 헛다리를 짚었고, 그 함정을 시험 주석에 적어 두었다).
전제(펼치기 전에 따라가기가 실제로 돌고 있었다)도 함께 단언해 시험이 헛돌지 않게 했다.
돌연변이로 확인: `stopGlide()`를 지우면 새 시험과 기존 `펼침…` 시험이 **둘 다** 깨진다.

### 이 회차의 교훈

검사가 깨질 때 '앱이 옳고 검사가 약하다'로 넘어가기 전에 **그 값을 누가 놓았는지 먼저 재라.**
`Element.prototype.scrollTop`의 setter를 감싸 스택을 남기는 것으로 충분했고, 그 한 번의 계측이
앞 회차의 오판을 뒤집었다. 화면이 '잠잠해 보인다'는 것은 '움직일 것이 남지 않았다'와 다르다.

## 추가 정밀 검토 — 2026-09-06 (앞 회차 결함의 '부류' 훑기 · 종단 재확인)

앞 회차의 결함은 한 문장으로 줄면 **"앱이 따라가지 않기로 정했는데, 이미 도는 미끄러짐은 그것을 모른다"**였다.
이번 회차는 그것을 *부류*로 보고 같은 모양이 더 있는지 훑었고, 그동안 다른 세션이 backend를 여러 곳 고쳤으므로
**계약이 어긋나지 않았는지 종단으로 다시 맞췄다**. **production 결함은 나오지 않았다.**

### 확인한 것

### 결함이 아니라 '좁혀 둔 계약'으로 확인한 것 (재조사 금지)

`splitRow`(차트 라벨)와 GFM('표로 보기')을 800건 무작위 셀로 대조해 어긋나는 자리를 전부 뽑았다.
둘 다 **코드가 스스로 좁혀 둔 자리**이지 새 결함이 아니다.

- `splitRow`는 서버가 쓰는 두 글자(`\|`·`\\`)만 되돌린다(주석에 그렇게 적혀 있다). 모델이 손으로 쓴 표에서
  `\*`·`\_`처럼 다른 문장부호를 이스케이프하면 GFM은 역슬래시를 떼고 차트 라벨은 남긴다 — 라벨에 역슬래시가
  하나 더 보인다. 서버가 채운 표(`data: step N`)에서는 생기지 않는다.
- '표로 보기'의 칸은 markdown으로 그려지므로, 조회 값에 `*`·`` ` ``·`[]`가 있으면 그 표기가 적용된다
  (`a*b*c` → `abc`). 온전한 값은 차트 툴팁(`full`)과 ⚡ 패널의 표(글자 그대로 그린다)에 늘 있다.
  프런트만으로 고치려면 표 markdown을 우리가 이스케이프해야 하는데, 그 글자는 이력으로 모델에게도
  가므로(서버가 쓴 표를 우리가 다시 손대는 셈이다) 값에 비해 위험이 크다 — 고치려면 서버의 `escapeCell`이다.
