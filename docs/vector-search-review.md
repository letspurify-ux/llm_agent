각 결함은 정식 테스트에서 실패를 확인한 뒤 수정했다. 기존의 청크별 trim 테스트는 내부 공백을
보존하는 새 계약으로 변경했으며, 문서 전체의 바깥 공백만 정리한다. 정상 테스트용 임베딩도 실제
스키마와 같은 1024차원으로 변경하여 차원 검증을 우회하지 않는다.

## 최종 검증

- `cd backend && npm test`: 524개 통과, 실패/건너뜀 0개.
- `cd backend && npm run test:integration`: 41개 통과, 실패/건너뜀 0개.
- `cd frontend && npm test`: 149개 통과, 실패/건너뜀 0개.
- 실제 Chrome의 검색 진행→결과 패널 전환 테스트: 1개 통과. 전체 UI 테스트 실행으로 간주하지 않는다.
  실행 명령: `cd frontend && node --test --test-concurrency=1 --test-name-pattern='검색·조회가 도는 동안' test/ui/ui.test.mjs`.
- 부분 누락·Unicode 이름 결함은 수정 전 정식 테스트의 실패를 확인했다. 수정 후 누락된
  청크만 재임베딩되고, 정상 쿼리명이 임베딩 없이 검색되어 프롬프트에도 온전히 실렸다.
- 실제 DB의 처리방법 검색에서 등록 순서와 다른 본문 순서대로 쿼리 후보가 표시되는지 확인했다.
  한글 조사와 한 글자 이름을 인식하고, `_`를 와일드카드로 오인하여 다른 이름을 고르지 않았다.
- 문자열 비교 충돌을 실제 DB에서 재현했다. 수정 전 다른 쿼리의 실행 함수 호출이 1회였고,
  수정 후 0회이며 미등록 오류가 기록됐다. 정확 검색·본문 라우팅 모두 다른 Unicode 이름을
  제외하고 정상 이름과 대소문자 변형은 그대로 반환하는 정식 회귀 검사를 추가했다.
- 정식 테스트에 시드가 고정된 1,000개 문서의 분할·병합 원문 보존 검사를 포함했다.
  별도 검토에서도 공백·반복 문구·이모지를 섞은 5,000개 문서의 원문 불일치가 0건이었다.
- 1,000행 테스트 데이터의 실제 EXPLAIN에서 정상 검색은 벡터 `embedding` 인덱스와 원본 PK
  `eq_ref` 조회를 사용했다. 정상 검색은 1회 조회, 무효 후보 발생 시 총 2회 조회였다.
- 기존 영벡터·극소 벡터 복구 SQL의 멱등성, 정상 벡터 보존, 누락분만 재임베딩을 검증했다.
- 캐시에서 퇴출된 이전 요청의 늦은 실패가 같은 검색어의 새 진행 중 요청을 지우지 않는지
  정식 회귀 테스트를 추가했다. 새 요청을 중복 호출하지 않고 정상 결과를 공유했다.
- 실제 DB의 등록명 1,000건에서 이름 메타데이터는 `query_name` 커버링 인덱스를 사용했고,
  본문 상위 30건의 상세만 읽었다. 총 DB 조회는 2회, 최종 테스트의 대조·상세 조회 실측은 4.1ms였다.
  데이터 규모나 환경 전반의 지연 시간 보장으로 해석하지 않는다.
- 이름 메타데이터 확인과 상세 조회 사이 등록명이 바뀌면 다른 SQL을 반환하지 않는지 검사했다.
  정확 이름 보충과 처리방법 라우팅 두 경로 모두 현재 이름을 재검증했다.
- 일반 자연어의 정확 이름 조회가 실패할 때 등록명 메타데이터 전체를 읽지 않고 UNIQUE 인덱스 조회
  1회 뒤 벡터 검색으로 이어지는지 정식 회귀 테스트로 고정했다.
- 저장 중 종료 요청을 배치 실패·행별 재시도 성공/실패·배치 성공·임베딩 행별 복구의 5가지 조합으로
  검증했다. 새 쓰기는 중단되고 실제 성공/실패만 집계되며, 다음 실행에서 미처리 행만 복구한 뒤
  다시 실행하면 재임베딩이 0건이었다. 진행 중인 DB 문장을 즉시 취소한다는 보장은 포함하지 않는다.
- 수동 복구 SQL을 실행하지 않은 상태에서도 영벡터와 극소 벡터가 검색 결과에 나오거나 정상 후보를
  가리지 않는지 실제 DB에서 검증했다. 극소 벡터는 수정 전 19건이 잘못 반환됐고 수정 후 0건이었다.
  정상 검색의 EXPLAIN은 변경 후에도 VECTOR `embedding` 인덱스와 원본 PK `eq_ref`를 사용했다.
- 긴 지식의 청크 트랜잭션에서 첫 쓰기 직후 종료 신호를 주는 정식 테스트를 추가했다. 수정 후
  추가 쓰기·커밋은 0건, 롤백은 1건이며 다음 실행이 전체 청크를 복구하고 세 번째 실행은 0건이었다.
- `git diff --check` 통과.

실행 환경은 Node.js 25.9.0, MariaDB 12.2.2였다. 통합 테스트는 기존 DB와 분리된 임시 Unix 소켓
DB를 사용하고, 임베딩 응답은 정상·실패·잘못된 값·순서 변경을 제어하는 대역으로 검증했다.
소켓을 사용하는 전체 테스트는 샌드박스의 `listen EPERM`을 확인한 뒤 승인된 환경에서 재실행했다.
위 통과 수는 해당 재실행 결과이며, 권한 오류를 코드 결함이나 성공으로 처리하지 않았다.

추가 점검에서는 현재 설정된 실제 `bge-m3` 서버의 2개 응답이 모두 1024차원이고 정규화 후
길이가 약 1임을 확인했다. 실제 모델과 임시 MariaDB를 연결한 별도 전체 경로 검증도 통과했다:
지식·처리방법·쿼리 각 1건을 임베딩·저장하고 동일 입력으로 검색하여 각각 1건, 거리 0으로 찾았다.
변경 없는 두 번째 동기화에서는 재임베딩이 0건이었다.

현재 설정된 기존 관리 DB는 직접 연결 검사에서도 `ECONNREFUSED`로 연결이 거부되었다.
따라서 기존 데이터에 대한 검색은 확인하지 못했다. 이는 임시 DB에서 검증한 코드 동작과 구분한다.

## 적용 및 성능 고려

코드 반영 후 첫 동기화에서 기존 v3 청크는 자동으로 재분할된다. 기존 자리는 seq를 유지하고,
텍스트 해시가 바뀐 청크만 다시 임베딩한다. 스키마 변경은 없다.

이전 버전에서 불량 벡터가 저장됐던 설치는 `backend/sql/repair-invalid-vectors.sql`을 관리 DB에
한 번 실행한 뒤 `npm run embed`로 누락분을 다시 계산한다. 실행 예시는 README의 벡터 검색 절에 있다.
복구 SQL은 정상 단위 벡터와 원본을 보존한다. 운영 DB의 복구·서버 배포는 이번 코드 검증에 포함하지 않았다.

정확 검색 보충은 무효 후보가 실제로 있을 때만 수행한다. 이 경로는 전체 행에 비례한 비용이 들 수
있으며 `MARIADB_TIMEOUT_MS`의 제한을 받는다. 정상 데이터에서의 인덱스 경로와 장애 시 정합성을
각각 테스트했고, 모든 데이터 규모에서 일정한 지연 시간이나 완전한 ANN 재현율을 보장하지 않는다.
정상 ANN 경로는 상위 후보 최대 60개의 벡터 노름을 추가 계산한다. 이는 기존 불량 벡터가 올바른
해시를 가진 채 남아 있어도 검색을 오염시키지 않기 위한 비용이며 DB 왕복은 늘리지 않는다.
불량 후보가 실제로 발견될 때만 기존의 정확 보충 조회가 한 번 추가된다.
청크 누락 검증은 이미 수행하던 집계에 값만 추가하므로 DB 왕복이나 원문 전송을 늘리지 않는다.
정확 쿼리명이 기존 UNIQUE 인덱스에서 확인되면 1회 조회다. 일반 한글·숫자·이모지 이름과 대부분의
ASCII 이름이 확인되지 않아도 1회 조회 뒤 벡터 검색으로 진행한다. DB와 JavaScript의 Unicode 변환
결과가 달라질 수 있는 비ASCII 대소문자 문자·결합 문자, `K`의 소문자형과 구분할 수 없는 `k`가
포함된 미적중 이름만 이름·번호 목록을 1회 보충 조회하며, 일치하면 그 PK의 상세를 1회 더 읽는다.
이 Unicode 보충 적중은 최대 3회 조회다.
처리방법 라우팅은 등록명 메타데이터 조회와 상위 30건 상세 조회의 최대 2회다. 기존 1회보다
왕복은 늘지만 긴 SQL·설명을 등록 건수만큼 읽지 않으며, 정확 조회·실행과 이름 비교가 일치한다.
메타데이터 스캔 비용은 등록 건수에 비례한다. 잘못된 이름 결과를 피하기 위해 요청 사이 캐시는 두지 않는다.

## 요구사항별 완료 확인

1. 전체 검색 코드 검토: 위 범위표의 생성·동기화·벡터/이름 검색·라우팅·에이전트 제어·근거 표시 경로와
   `context.md`의 검색 계약을 대조했다. 인덱스 경로, 실패 시 복구, 반복 제한, 결과 표시를 각각 검증했다.
2. 실제 결함 확정 후 수정: 위 결함마다 수정 전 실패를 재현했다. DB의 collation·거리 계산·인덱스
   동작은 대역의 추측으로 확정하지 않고 실제 MariaDB에서 검증했다.
3. 수정 후 정상 동작: 백엔드와 DB 통합 테스트에 실패·건너뜀이 없다. 프런트엔드는 변경 없이 기존
   전체 단위 테스트와 실제 Chrome 검색 화면 검증 결과를 유지한다. 기존 운영 DB 데이터 확인은
   연결 거부로 수행하지 못했으며, 이를 코드 테스트 성공에 포함하지 않았다.
4. production 결함의 정식 테스트: 재현 검사는 `backend/test`의 일반 또는 통합 테스트에 포함했다.
   일회성 실험만으로 수정 완료를 판정하지 않았다. 정상 경로와 장애 복구도 함께 검사한다.
