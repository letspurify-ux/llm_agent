# 컨텍스트 관리 정밀 검토 — 2026-09-08

컨텍스트의 검색·보관·표시·실행·결과 재사용·최근 대화 경로를 현재 [계약](../context.md)과 대조했다. 운영 코드 결함 3종을 수정 전 실패로 재현하고 수정했다. 정식 회귀 테스트는 최상위 11개와 하위 사례 4개를 추가했다. 최종 전체 테스트 **819개가 통과**했으며 실패·취소·건너뛰기는 없다.

## 1. 프롬프트에서 잘린 실행 파라미터로 다른 조회가 실행됨

실행 이력의 긴 바인드 값은 앞 205 UTF-16 코드 유닛과 `…(생략)`으로 표시됐다. 실행 가드는 결과 셀과 최근 대화에서 잘린 조각을 기록했지만 **실행 이력의 파라미터는 기록하지 않았다**. 모델이 표시만 떼고 재사용하면 짧아진 값을 정상 바인드로 실행했다. 여러 파라미터의 합이 500자를 넘으면 JSON 전체를 잘라 마지막 값을 임의 길이 조각으로 만드는 문제도 있었다.

수정 전 실제 Oracle에서 `:memo = RPAD('x', 350, 'x')` 조건은 원본 바인드로 1행을 반환했다. 프롬프트에서 복사한 205자 조각으로 재조회하면 가드를 통과해 0행을 반환했다. 이력의 파라미터 JSON이 끝나기 전에 끊기는 실패도 정식 테스트로 확인했다.

- [prompt-values.js](../backend/src/prompt-values.js)에서 표시 변환을 공유한다. 값별 절단 뒤에는 바인드 단위로 생략하고, 생략 건수까지 500자 안에 넣는다. 뒤에 있는 짧은 식별자도 예산에 들어가면 표시한다.
- [agent.js](../backend/src/agent.js)는 각 결정 호출 전에 실제 표시되는 파라미터의 절단 조각을 기록한다. 성공·실패한 조회 모두 적용하고, 표시 변환의 오류는 기존 결정 호출의 예외 처리 안에서 처리한다.
- 원본 바인드와 일반 입력은 허용하며, 표시에서 완전히 빠진 값의 접두사를 절단 근거로 등록하지 않는다.

정식 테스트: [context-flow.test.js](../backend/test/context-flow.test.js)의 성공·실패 × 일반 문자열·서로게이트 경계 4개 사례, [prompt.test.js](../backend/test/prompt.test.js)의 JSON·이스케이프·제어문자·생략 범위, [Oracle 통합 테스트](../backend/test/oracle/oracle.test.js)의 실제 조회를 추가했다. 수정 후 잘린 조각은 조회 결과로 남지 않고 실행 경계에서 거부된다.

## 2. 스키마가 허용하는 대상 DB 이름이 잘리거나 거부됨

`target_db.db_name`의 `VARCHAR(100)`은 문자 수를 세지만 프롬프트·결정·실행 경계는 JavaScript 문자열 길이 100을 상한으로 사용했다. 보충 평면 문자는 UTF-16 코드 유닛 2개를 차지하므로, DB에 정상 등록되는 이름이 중간에서 잘리거나 선택할 수 없게 됐다.

수정 전 실제 MariaDB에 `'조회_😀'.repeat(25)`를 저장하면 `CHAR_LENGTH`는 100이며 원문도 유지됐지만, 검색 후 후보 프롬프트에서는 식별자가 잘렸다. 100개 이모지로 만든 이름도 결정·실행 선택 테스트에서 실패했다.

- [constants.js](../backend/src/constants.js)의 공통 대상 DB 이름 상한을 200 UTF-16 코드 유닛으로 맞췄다. 프롬프트·결정·실행 경계가 같은 값을 사용한다.
- 이력 예산 계산은 개별 파라미터 하나의 실제 절단 길이 대신 파라미터 전체 몫 500자를 계산하도록 수정했다. 이력 기본 몫은 29,000자로 보장한다. 기존 배분에서도 이력은 다른 섹션의 기본 몫을 남긴 29,500자까지 받을 수 있었으므로, 이 보장 변경으로 다른 섹션의 실제 몫을 줄이지 않는다. 전체 자료 예산은 80,000자다.

정식 테스트: [prompt.test.js](../backend/test/prompt.test.js)의 후보·상세·실행 이력, [oracle.test.js](../backend/test/oracle.test.js)의 결정 → 대상 선택 → mock 실행, [MariaDB 통합 테스트](../backend/test/integration/mariadb.test.js)의 실제 스키마 등록 → 실제 검색 → 결정 → mock 조회 → 실행 이력 경로를 추가했다. 상한을 넘는 이름으로 접두사가 같은 다른 DB를 실행하지 않는 기존 회귀 테스트도 통과했다.

## 3. 실제 `…` 컬럼이 생략 안내와 충돌해 값이 바뀌거나 사라짐

드라이버의 컬럼 수 제한과 프롬프트의 길이 제한이 모두 `…`라는 컬럼 이름을 생략 안내로 사용했다. 실제 컬럼명이 `…`이면 넓은 결과를 저장하면서 원래 값을 덮어쓰거나, 프롬프트에서 숫자 `42`를 안내 문자열로 바꿨다. 표·차트 조립에도 이름이 `…`인 열을 무조건 제외하는 코드가 있었다.

수정 전 단위 테스트와 실제 Oracle의 `SELECT 42 AS "…", ... FROM DUAL`로 재현했다. 저장·프롬프트 경로를 수정한 뒤에도 최종 표가 `42`를 제외하는 실패를 확인하고, 표·차트까지 같은 결함의 소비 경로를 수정했다.

- [result.js](../backend/src/result.js)에서 시스템이 만든 생략 안내에 요청 내부 메타데이터를 붙인다. 안내 이름은 실제 컬럼과 충돌하지 않게 고르며, 드라이버에서 생략된 실제 컬럼명도 피한다.
- [oracle.js](../backend/src/oracle.js)와 [llm-openai.js](../backend/src/llm-openai.js)는 실제 데이터와 안내를 구별하고 두 단계의 생략 사유를 함께 보존한다.
- [read-result.js](../backend/src/read-result.js)는 컬럼 선택으로 새 표시 행을 만들 때도 그 구분을 유지한다.
- [chart.js](../backend/src/chart.js)는 메타데이터로 판정한 안내만 제외한다. 실제 `…`, `……` 컬럼의 이름·값·타입은 유지하며, 행마다 안내 이름이 다른 경우에도 안내를 다른 행의 데이터 셀에 넣지 않는다. 메타데이터 자체는 JSON이나 사용자 출력에 직렬화되지 않는다.

정식 테스트: [oracle.test.js](../backend/test/oracle.test.js)의 저장 충돌, [prompt.test.js](../backend/test/prompt.test.js)의 30·40열 및 컬럼 선택 전후, [chart.test.js](../backend/test/chart.test.js)의 표·차트 값·축·행별 안내 구분, [Oracle 통합 테스트](../backend/test/oracle/oracle.test.js)의 보관 → 추가 읽기 → 프롬프트 → 표·프런트엔드 차트 파서까지 추가했다. 실제 값 `42`와 두 단계의 생략 사유가 각각 보존된다.

## 최종 검증

| 테스트 묶음 | 시작 시 기준선 | 수정 후 최종 |
| --- | ---: | ---: |
| 백엔드 `npm test` | 534 | 546 |
| 실제 MariaDB `npm run test:integration` | 45 | 46 |
| 실제 Oracle `npm run test:oracle` | 10 | 12 |
| 프런트엔드 `npm test` | 149 | 149 |
| 실제 Chrome `npm run test:ui` | 64 | 64 |
| 프로덕션 빌드 `npm run test:production` | 2 | 2 |
| 합계 | **804** | **819** |

양쪽 디렉터리에서 `npm run test:all`을 실행했다. 정식 테스트 수는 Node 테스트 실행기의 집계이며 최상위 테스트와 하위 사례를 포함한다. 새 결함 회귀는 최상위 11개 + 하위 4개 = 15개다. 기존 검색 경계 테스트 등 작업 시작 시 있던 변경은 새 회귀 수에 포함하지 않았다.

검토 도중 별도 변경된 검색 거리 문턱 `0.4`는 유지했다. 기존 검색 경계 테스트의 상위 20건 데이터는 문턱 안에 배치하고, 경계 사례를 `0.39` 포함·`0.41` 제외로 맞췄다. 실제 MariaDB에서 세 소스 모두 순서·상한·거리 필터·정상 0건이 통과했다. 현재 계약 문서에도 `0.4`를 반영했다. 이 조정은 위 3종 결함과 별개다.

추가 탐색 검증도 실행했다. 파라미터 10,000조합에서 JSON 유효성·500자 상한·표시된 절단 조각의 가드 일치를 확인했다. 검색·확대·숨김·복구·조회·추가 읽기를 섞은 1,000개 요청, 9,772번 결정에서 ID·보관 청크 보존, 표시 중복 없음, 문서별 10,000자 상한, 이력 줄 수, 전체 행과 미리보기 분리를 확인했다. 이 탐색의 최대 프롬프트는 29,372자였으며, 최대 예산을 채우는 경우는 별도의 기존 정식 예산 테스트가 검증한다.

검증 환경은 Node.js v25.9.0, 임시 MariaDB, 별도 Oracle 컨테이너와 실제 Chrome이다. 테스트의 임시 DB·브라우저 자원은 종료 시 정리한다. 최종 `git diff --check`도 통과했다.

## 검증의 범위

미해결로 남긴 재현 가능한 컨텍스트 코드 결함은 없다. 실제 업무 DB나 운영 계정은 사용하지 않았다. LLM 결정과 임베딩은 제어된 응답으로 검증했으므로 실제 모델의 의미 검색 품질이나 답변 정확도에 대한 평가는 포함하지 않는다. 정적 검토와 경계·통합·브라우저 테스트를 통과했다는 결과이며, 가능한 모든 입력에서 결함이 없다는 수학적 보증은 아니다.
