# context.md·지식·처리 방법·쿼리 경로 정밀 검토

검토일: 2026-09-06

현재 `context.md`를 기준으로 검색에서 답변까지 관련 운영 코드를 읽고, 의심 증상을 재현한 뒤 수정했다. 이번 검토에서 확정한 결함은 두 종류다. 기존 작업의 수정 사항은 유지했다.

## 범위

| 경로 | 검토 코드 및 확인 사항 |
| --- | --- |
| 지식 저장·검색 | `chunk.js`, `embed-sync.js`, `embedding.js`, `search.js`, `db.js`: 청크 경계·병합·원문 판본·임베딩 동기화·소스별 벡터 검색·정확한 쿼리명 검색·검색 실패와 0건 구분 |
| 컨텍스트 관리 | `context-items.js`, `agent.js`, `llm-openai.js`, `constants.js`: ID 보존·확대·숨김·복구·자료 예산·실행 이력·행동 제한·LLM 응답 처리 |
| 처리 방법·쿼리 실행 | `llm.js`, `sql.js`, `oracle.js`, `numbers.js`: 방법 본문의 쿼리 연결·직접 검색·대상 DB 선택·바인드 정규화·조회 가드·타입과 정밀도 보존 |

| 저장 구조 | `schema.sql`, `migrate-chunk.sql`, 시드 SQL: 원문·청크·벡터 관계, 재실행 및 변경 반영 |

## 확정 결함과 수정

### 1. TIMESTAMP의 밀리초 소실

`oracle.js`의 날짜 변환기가 드라이버가 확보한 밀리초를 버렸다. 실제 Oracle에서 `2026-09-06 12:34:56.123`과 `.456`을 조회하면 두 값 모두 `2026-09-06 12:34:56`으로 반환됐다. 서로 다른 시각이 프롬프트와 추가 읽기에서 같아지고, 후속 조회 바인드와 차트의 시간 축에서도 구별되지 않는 운영 코드 결함이다.

- 수정 전: 단위 회귀 테스트와 실제 Oracle 통합 테스트에서 값이 같아지는 실패를 확인했다.
- 수정: `DATE`는 기존 초 단위를 유지하고, `TIMESTAMP`, `TIMESTAMP WITH TIME ZONE`, `TIMESTAMP WITH LOCAL TIME ZONE`은 밀리초를 보존한다. 세션의 TIMESTAMP 포맷에도 `FF3`를 적용했다.
- 수정 후: 실제 Oracle 결과 → `read_result` → 프롬프트 → 후속 바인드에서 두 번째 행만 정확히 조회했다. 프런트엔드 차트 파서에서도 두 시각의 차이가 333ms로 유지된다.
- 정식 테스트: `backend/test/oracle.test.js`와 `backend/test/oracle/oracle.test.js`에 각각 1개 추가했다.

포맷 제약도 `context.md`에 명시했다. LTZ에 오프셋 포함 문자열을 바인드할 때는 등록 SQL에서 `TO_TIMESTAMP_TZ`로 해석해야 한다. 드라이버의 JavaScript Date보다 높은 정밀도가 필요하면 조회 SQL에서 `TO_CHAR(..., 'YYYY-MM-DD HH24:MI:SS.FF9')`로 반환하고 후속 조회에서 같은 포맷으로 변환한다. 이 문자열 경로는 실제 Oracle에서 9자리 소수 초의 왕복을 확인했다. 이번 변경이 드라이버의 밀리초 해상도 자체를 높이는 것은 아니다.

### 2. 없는 결과 컬럼에 프로토타입 값 표시

`llm.js`의 대체 답변과 `chart.js`의 표·차트 참조는 셀을 읽을 때 일반 속성 접근을 사용했다. 결과 컬럼에 `__proto__`나 `constructor`가 있고 어떤 행에는 해당 속성이 없으면, 빈 셀에 `[object Object]`나 `function Object() { [native code] }`가 표시됐다.

- 수정 전: 일부 행에만 해당 컬럼이 있는 결과로 실제 답변 조립 함수를 호출해 잘못된 셀 표시를 재현했다.
- 수정: 세 경로에서 공통 `ownProp` 헬퍼로 행 자체의 속성만 읽도록 변경했다.
- 수정 후: 없는 셀은 빈칸이고, 같은 이름으로 실제 저장된 값은 그대로 표시된다.
- 정식 테스트: `backend/test/llm.test.js`와 `backend/test/chart.test.js`에 각각 1개 추가했다.

## 검증 결과

| 실행 | 결과 |
| --- | --- |
| 수정 전 백엔드 기준선 `npm test` | 441개 통과 |
| 결함 재현 | 새 단위 회귀 테스트 3개와 실제 Oracle 회귀 테스트에서 수정 전 실패 확인 |
| 수정 후 백엔드 `npm run test:all` | 단위 444개 + 실제 MariaDB 9개 + 실제 Oracle 9개 = 462개 통과 |
| 프런트엔드 `npm test` | 126개 통과 |
| 추가 실제 MariaDB 벡터 조회 | 긴 문서 뒤쪽 적중·처리 방법·쿼리 설명 검색·무관한 검색 0건·에이전트 프롬프트 전달 통과 |

최종 정식 테스트에서 실패·건너뛰기는 없다. 프런트엔드 최초 추가 실행은 샌드박스의 로컬 서버 실행 제한으로 실패했으며, 해당 권한이 허용된 실행에서 전부 통과했다.

추가 벡터 검증은 임시 MariaDB의 실제 `VECTOR(1024)` 인덱스와 검색 SQL을 사용했다. 10,690자 앞부분 뒤에 배치한 내용이 14번째 청크에서 검색됐고, 관련 처리 방법과 쿼리 각 1건이 프롬프트에 전달됐다. 무관한 검색어는 세 대상 모두 0건이었다. 이는 제어된 임베딩으로 저장·검색·연결을 검증한 것이며 실제 임베딩 모델의 의미 검색 품질을 평가한 결과는 아니다.

정식 테스트 추가는 확인된 운영 코드 결함에 대응하는 **4개(단위 3개·Oracle 통합 1개)**로 제한했다. 결함이 발견되지 않은 추가 벡터 확인은 임시 스크립트로 실행했으며 정식 테스트에 편입하지 않았다.

검증에는 임시 MariaDB와 별도 Oracle 컨테이너를 사용하고 종료 후 정리했다. 운영 DB와 실제 업무 데이터에 대한 실행, 실제 LLM의 답변 품질 평가는 포함하지 않았다.
