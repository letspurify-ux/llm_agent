# 중첩 렌더링 정밀 검토 — 2026-09-09

LaTeX·Markdown·chart·Mermaid의 기존 조합 검사를 확장해, 문법이 다른 문법의 내부에 들어갈 때의 원문·셀 경계·실제 그림을 검증했다.

## 재현한 결함과 수정

| 결함 | 수정 |
|---|---|
| 표 안 시각화의 내부 백틱이 바깥보다 길면 일부를 닫는 기호로 오인해 본문과 오른쪽 셀이 잘림 | 백틱 런의 길이가 정확히 같은 짝만 연결하는 공통 스캐너를 서버와 프런트에서 사용 |
| 일반 코드 예시 안의 `mermaid`를 다시 변환해 임시 토큰이 노출됨 | 바깥 코드 범위를 먼저 소비하고, 여러 물리적 줄에 걸친 일반 코드도 Markdown AST로 보호 |
| LaTeX가 시각화 모양의 문자열을 포함하면 수식과 오류 원문에 `LLMRICHTABLE` 토큰이 노출됨 | 임시 토큰마다 원문 전체를 보관하고, 수식 본문·오류 폴백을 만들 때 원래 백틱까지 복원 |
| 링크 주소·참조 식별자·이미지 주소·HTML 속성의 코드 표기를 시각화로 변환하거나 조회 데이터로 치환함 | 파서가 확정한 문법 범위로 본문과 주소·속성을 구분. 서버에 `mdast-util-from-markdown`을 추가하고 보호 판정을 공통 모듈로 통일 |
| 코드 안쪽에 패딩 공백이 있으면 시각화 인식과 표 보호가 어긋남 | 보호·주입·최종 렌더의 언어 판정을 일치시킴 |
| 미완성 수식 반복 입력에서 기존 성능 검사가 실패함 | GFM 자동 링크의 불가능한 후보를 `previous` 단계에서 제외해, 불필요한 텍스트 이벤트 분할과 병합 비용을 줄임 |

수정 전 성능 실패는 원본에서도 재현했다. CPU 프로파일에서 대부분의 시간이 micromark의 `resolveAllText`에 집중됐다. 이 함수가 인접 텍스트 이벤트를 반복 `splice`하는 동안, GFM이 이메일이 될 수 없는 영숫자까지 후보로 분할하고 있었다. 실제 링크의 파싱은 기존 GFM에 맡기고, 원문에 필요한 `@`·프로토콜·`www.`가 없는 후보만 제외했다. 테스트 기준은 완화하지 않았다.

같은 로컬 환경에서 `\[ x ` 16,000회(80,000자)의 렌더 중앙값은 약 246ms에서 44ms로 감소했다. 이는 특정 입력의 로컬 측정이며 모든 문서·기기의 성능을 보장하는 수치는 아니다. 문서 끝에 실제 이메일을 붙인 경우도 별도로 확인했다.

## 검증 범위

- 시각화 2종 × 바깥/안쪽 백틱 길이 12쌍 × 인라인 래퍼 3종 × 목록·인용 래퍼 5종 × 개행 3종 = 1,080개 입력. 각각 최종 렌더와 스트리밍 미리보기를 검사한다.
- 일반 코드, LaTeX 성공/오류 폴백, 링크·이미지·참조 정의·HTML 속성, 패딩 공백, 서버 조회 주입, 수신 중인 모든 접두사의 원문과 이웃 셀을 확인한다.
- GFM 최적화는 195개 문서를 기존 GFM과 HTML로 비교하고, 같은 파서를 재사용해 AST와 상태 복원도 비교한다.
- 실제 앱에서는 `목록 → 인용 → 표 → 강조 → Mermaid → LaTeX`와 같은 표의 조회 차트·일반 코드·수식·링크를 1,000px와 320px에서 검사한다. SVG, MathML, 차트, 오른쪽 셀, 페이지 넘침, 콘솔 오류, 임시 토큰을 확인한다.
- 기존 200개 수식 표, 표 링크, 혼합 콘텐츠, 스트리밍·리셋·재시도, 이미지 자동 요청 방지, 배포 번들 검사도 함께 실행한다.

주요 회귀 검사는 [nested-boundaries.test.js](../frontend/test/nested-boundaries.test.js), [gfm-boundaries.test.js](../frontend/test/gfm-boundaries.test.js), [rendering-browser.mjs](../frontend/test/review/rendering-browser.mjs)에 있다.

## 실행

```sh
npm --prefix backend test
npm --prefix frontend run test:regression
```

검증 결과: 프런트엔드 단위 검사 299개, 백엔드 검사 565개, Chrome UI 검사 87개,
배포 빌드 검사 3개가 통과했다. 배포 검사에는 11개 실제 앱 사례를 두 화면 폭에서
검사하는 22회 조합 검증이 포함된다. 마지막 공통 코드 경계 수정 후 영향받는
프런트엔드 조합 검사 20개와 백엔드 차트 검사 37개도 재확인했다.

DB·LLM을 호출하지 않고 고정된 조회 결과와 응답으로 검증한다. 실제 데이터 조회 내용의 정확성은 이번 렌더링 검토의 대상이 아니다. Mermaid 자체의 문법 오류나 KaTeX 미지원 명령은 기존처럼 해당 원문을 확인할 수 있는 폴백으로 남긴다.
